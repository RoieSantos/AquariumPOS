# Changelog

Dated log of code changes made to this project (see CLAUDE.md's "Changelog" instruction). Newest entries at the top.

## 2026-09-19

- Pivoted the group-chat-with-Alice feature to live entirely inside the portal, per "i want alice and the GC to live only in the portal" (no external Telegram app). Discovered the portal already has a full Messenger-style DM widget (`docs/js/chat.js`, schema in `supabase_portal_chat_tables.sql`) with `IsGroup` already reserved for a "planned follow-up" group feature - built that follow-up now instead of a bespoke new page:
  - New [supabase_portal_chat_groups_and_alice.sql](sql/supabase_portal_chat_groups_and_alice.sql): adds `create_group_conversation()` (multi-member group creation) and a synthetic `StaffUsers` row for `'alice'` (`IsActive=true`, unguessable random password hash - shows up as a normal contact in the chat directory but can never actually log in), plus `is_alice_conversation_member()`.
  - New `supabase/functions/portal-chat-alice-reply/index.ts`: generates Alice's replies inside portal chat, reusing the same shared engine as Messenger/website Alice in `simulate: true` mode (same safety net as the AI Bot Sandbox - no real orders/escalations/CRM saves from here). DM her directly and she always replies; add her to a group and she only replies when a message contains "@Alice" - re-verified server-side, not just trusted from the client.
  - `docs/js/chat.js`: added a "New Group" tab (multi-select staff + group name) alongside the existing 1:1 "New Message" flow, sender-name labels on group message bubbles, and the client-side trigger that calls the new function and broadcasts Alice's reply live to everyone in the conversation. New `.chat-new-tabs`/`.chat-msg-sender` styles in `docs/css/styles.css`.
  - The earlier Telegram-based approach (`supabase_telegram_alice_messages.sql`, `supabase/functions/telegram-alice-webhook`) stays deployed but is now dormant/unused (its webhook was never registered with Telegram) - left in place rather than deleted in case it's wanted later; say the word if you'd rather it be removed.
- Added @mention autocomplete to the portal chat thread input, per "when I put @ there are no users to be tagged" - typing "@" now opens a dropdown of the OPEN conversation's other members (filtered as you keep typing, navigable with arrow keys/Enter/Tab, Escape to dismiss) instead of requiring staff to already know someone's exact username, including Alice's. `docs/js/chat.js` (candidate list populated from the conversation's real membership each time a thread is opened) + new `.chat-mention-dropdown`/`.chat-mention-item` styles in `docs/css/styles.css`.
- Made URLs inside portal chat messages clickable, per "can you make the link clickable always" - Alice's quote replies often end with a drawing/preview link (`compute_aquarium_quote`'s URL) that was previously just inert text. New `chatLinkify()` in `docs/js/chat.js` (escapes the message first, then wraps bare URLs in a real `<a target="_blank">`, trimming trailing sentence punctuation off the link) + link-color styles in `docs/css/styles.css` for both message bubble colors.
- Restricted 1:1 DMs with Alice to super users only, per "staff can only tag alice on a GC, dont allow the non super user staff to talk to alice directly" - any staff can still @mention her inside a group they create, just not DM her directly. Enforced two layers: `docs/js/chat.js` hides her from the "Message" tab's directory for non-super users (still shown under "Group"), and `supabase/functions/portal-chat-alice-reply` refuses to generate a reply for a non-group conversation unless `is_admin_authorized` passes - the real enforcement point, since `get_or_create_dm_conversation` (supabase_portal_chat_tables.sql) never re-verifies identity at all.
- Gave Alice an honest way to say "I don't know that yet" instead of implying she already handled something she didn't (seen when staff asked about aquarium REPAIR service pricing, which she has no knowledge of, and she replied as if it had already been sent to staff for a price). New `log_capability_gap` tool (`supabase/functions/_shared/chatbot-engine.ts`) - distinct from `escalate_to_staff` (for things she CAN handle but need a human to finish) - for requests she genuinely has no knowledge/pricing/tool for at all. New system prompt section ("WHEN YOU DON'T ACTUALLY KNOW / CAN'T HELP") tells her to say so plainly (Taglish example included) and log it, never claim it was forwarded when nothing was. New [supabase_bot_capability_gaps.sql](sql/supabase_bot_capability_gaps.sql) (`BotCapabilityGaps` table + admin list/status RPCs, seeded with this exact repair-pricing incident) and a new "Capability Gaps / Enhancement Requests" review table on `docs/ai-bot-setup.html`/`docs/js/aiBotSetup.js` so staff can actually see and triage the backlog instead of it being invisible. Redeployed all five functions that bundle the shared engine (`facebook-messenger-webhook`, `chatbot-sandbox-reply`, `chatbot-web-reply`, `telegram-alice-webhook`, `portal-chat-alice-reply`).
